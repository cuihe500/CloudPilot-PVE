# 系统化调试

> 基线：官方 [obra/superpowers · systematic-debugging](https://github.com/obra/superpowers)。
> 本文件保留其骨架（铁律 → 四阶段 → 危险信号 → 借口对照 → 速查表），并针对 CloudPilot-PVE 的
> RBAC、配额、审批、幂等执行、PVE 请求与 LLM 结构化输出等边界做了定制。

## 概述

**核心原则：** 先找到根因，再动手修复。修表象即失败。
**违反流程的字面要求，就是违反调试的精神。**

## 铁律

```
未完成根因调查（阶段 1），不得提出修复。
```

## 何时使用

任何技术问题都适用：测试失败、生产 Bug、非预期行为、性能问题、构建失败、集成问题。

**尤其在以下情况不得跳过：**
- 有时间压力或“紧急上线”（越急越想猜）。
- “就改一行”看起来很显然。
- 已经试过多次修复仍未解决。
- 你并不完全理解这个问题。

**本仓库高风险场景，必须先走完流程再动手：** RBAC/资源归属、配额与容量边界、审批状态转换与计划摘要绑定、幂等键/重试/任务恢复、到期回收、PVE 请求构造与 UPID 状态、LLM 结构化输出的拒绝路径。

## 四个阶段

每个阶段完成后才能进入下一阶段。

### 阶段 1：根因调查

**动手修复前必须做到：**

1. **完整读取错误证据** — 错误、堆栈、退出码、`log/slog` 日志、PVE 任务的 UPID 状态，一行不跳。
2. **稳定复现** — 记录精确复现步骤；不能稳定复现就补观测，不猜。
3. **检查最近变更** — `git diff`、近期提交、新依赖、迁移、配置差异。
4. **在组件边界收集证据** — 本仓库典型链路为 `HTTP(Gin) → 服务层 → 任务队列 → PVE 客户端 → PVE`，以及 `LLM → 结构化请求 → 确定性校验(RBAC/配额/模板/网络/有效期) → 任务`。在每个边界打点确认「输入 / 输出 / context 传递 / 权限与配额判定结果」，先定位是哪一层断的，再深入该层。
   - 不要记录令牌、密码、Cloud-init 密钥或完整模型提示。
5. **逆向追踪数据流** — 坏值从哪里产生？谁用坏值调用了它？一路上溯到源头，在源头修，不在表象修。

### 阶段 2：模式分析

1. **找正常样例** — 在仓库中找相邻的、能正常工作的实现。
2. **对照参考实现** — 若在套用既有模式（如另一个 PVE 写操作、另一条审批转换），完整读完参考实现，不略读。
3. **列出差异** — 正常路径与异常路径的每一处差异都列出，不臆断“这不可能有关”。
4. **确认依赖与假设** — 需要哪些 context、超时、配置、权限、配额前置条件。

### 阶段 3：假设与验证

1. **提出单一假设** — 明确写出：“根因可能是 X，因为证据 Y”。
2. **最小实验** — 一次只改一个变量，做能证伪/证实该假设的最小改动。
3. **验证后再继续** — 成立 → 阶段 4；不成立 → 提出新假设，不要在旧修复上叠加。
4. **不懂就说不懂** — 明确“我不理解 X”，继续研究或请求确认，不假装理解。

### 阶段 4：实现修复

1. **先建失败测试** — 优先写能重现问题的最小自动化测试；修复前确认它失败。高风险逻辑（RBAC/配额/审批/幂等/回收/PVE 状态/LLM 拒绝路径）必须落测试。
2. **只做单一修复** — 在所有相关调用都会经过的**共享入口**修根因；不顺手重构，不夹带无关改动。
3. **验证修复** — 回归测试通过、其他测试未被破坏、问题确实消失。完成前使用 `verification-before-completion`。
4. **修复无效则停** — 数一下已尝试次数：
   - < 3 次：回到阶段 1，用新信息重新分析。
   - ≥ 3 次：**停止修改，质疑架构**（见下）。
5. **3 次以上失败：质疑架构** — 若每次修复都在别处引出新的共享状态/耦合问题，或都需要“大规模重构”，这不是失败的假设，而是错误的架构。**取得人工确认后再继续**；若触及生产 PVE、破坏性迁移、认证/授权/审批/配额语义，必须先获人工确认（见 `AGENTS.md` 第 8 节）。

## 危险信号 —— 立即停止，回到阶段 1

- “先快速修一下，回头再查。”
- “改改 X 看能不能好。”
- “一次多改几处再跑测试。”
- “跳过测试，我手动看看。”
- 追踪数据流之前就抛出解决方案。
- “再试最后一次修复”（已经试过 2 次以上）。
- 每次修复都在不同位置引出新问题。

## 常见借口对照

| 借口 | 事实 |
|------|------|
| “问题很简单，不用走流程” | 简单 Bug 也有根因，流程对简单 Bug 很快。 |
| “紧急，没时间走流程” | 系统化调试比猜-试-返工更快。 |
| “先随手试，再调查” | 第一次修复定基调，一开始就做对。 |
| “确认能修好再补测试” | 未测的修复留不住，先写失败测试。 |
| “一次多改几处省时间” | 无法隔离到底哪处生效，且引入新 Bug。 |
| “只在这个调用方加个特例” | 表象修复，兄弟调用方仍然坏。 |
| “用重试/延时/忽略错误绕过” | 掩盖未理解的问题，不是修复。 |

## 速查表

| 阶段 | 关键动作 | 完成标准 |
|------|----------|----------|
| 1. 根因 | 读错误、复现、查变更、边界打点、逆向追踪 | 弄清「是什么」和「为什么」 |
| 2. 模式 | 找正常样例、对照、列差异 | 找出关键差异 |
| 3. 假设 | 提单一假设、最小实验 | 证实或换新假设 |
| 4. 实现 | 建失败测试、单一修复、验证 | Bug 解决且测试通过 |

## 停止条件

- 连续两个假设失败：返回阶段 1 重新收集证据。
- 三次修复仍失败：停止修改，向用户说明可能存在架构问题。
- 触及生产 PVE、破坏性迁移、认证/授权/审批/配额语义：取得人工确认后继续。
