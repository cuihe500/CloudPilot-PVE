# 系统化调试

## 硬规则

没有根因证据，不修改代码。一次只验证一个假设，不叠加多个猜测性修复。

## 流程

1. **读取证据**
   - 完整读取错误、堆栈、退出码和相关日志。
   - 记录准确复现步骤；不能稳定复现时先补充观测，不猜。
2. **追踪来源**
   - 检查最近变更和所有相关调用者。
   - 从错误位置逆向追踪数据、状态和配置的来源。
   - 在组件边界确认输入、输出和上下文是否正确传递。
3. **对比模式**
   - 在仓库中寻找相邻的正常实现。
   - 列出正常与异常路径的实际差异。
4. **提出单一假设**
   - 明确写出：“根因可能是 X，因为证据 Y”。
   - 用最小实验验证该假设。
5. **建立回归检查**
   - 优先写能重现问题的最小自动化测试。
   - 修复前确认检查失败，修复后确认通过。
6. **修复根因**
   - 在所有相关调用都会经过的共享入口修复。
   - 不顺手重构，不同时处理无关问题。
7. **完整验证**
   - 运行回归检查和受影响的仓库检查。
   - 使用 `verification-before-completion` 后再报告完成。

## 停止条件

- 连续两个假设失败：返回证据收集阶段。
- 三次修复尝试仍失败：停止修改并向用户说明可能存在架构问题。
- 涉及生产 PVE、破坏性迁移、认证或授权语义：取得人工确认后继续。

## 禁止行为

- 只处理错误表象或仅在单个调用方加特例。
- 一次修改多个变量后用结果反推原因。
- 用重试、延时或忽略错误掩盖未理解的问题。
- 没有运行测试就声称问题已修复。
