# 完成前验证

> 基线：官方 [obra/superpowers · verification-before-completion](https://github.com/obra/superpowers)。
> 本文件保留其骨架（铁律 → 门禁函数 → 常见失败 → 危险信号 → 借口对照），并针对 CloudPilot-PVE 的
> `make check`、OpenSpec 验收、数据库迁移与 OpenAPI 契约做了定制。

## 概述

**核心原则：** 先有证据，再下结论，永远如此。
**违反字面要求即违反精神。** 没有本轮亲自运行的新鲜证据，不得声称完成。

## 铁律

```
没有当前工作树上的新鲜验证证据，不得声称完成或通过。
```

本条消息里没运行过的验证命令，就不能声称它通过。

## 门禁函数

```
在声称任何状态或表达满意之前：

1. 确定：哪条命令能证明这个结论？
2. 运行：执行完整命令（全新、完整，不用旧结果）。
3. 读取：完整输出 + 退出码 + 失败计数。
4. 核对：输出是否真的支持结论？
   - 否 → 用证据陈述真实状态。
   - 是 → 带证据陈述结论。
5. 才可以下结论。

跳过任何一步 = 在撒谎，不是在验证。
```

## 本仓库验证顺序

1. **确定结论** — 列出准备声称已满足的行为与 OpenSpec 验收场景。
2. **针对性检查** — 先跑直接证明该结论的最小测试（如 RBAC、配额、审批转换、幂等、PVE UPID 状态、LLM 拒绝路径）。
3. **统一入口** — 再跑 `make check`（提交前统一门禁）；契约相关改动确认 `make generate` 无漂移。
4. **检查变更** — 看 `git diff` 与 `git status`：无越界修改、无秘密、无生成文件漂移、无遗漏文档。
5. **对照规范** — 逐项核对已批准 OpenSpec 与 `AGENTS.md` 第 9 节「完成定义」，含 OpenAPI、迁移、生成代码是否同步。
6. **报告事实** — 列出运行过的命令、通过/失败结果与未验证项；失败就报失败，不弱化。

## 常见失败对照

| 结论 | 需要的证据 | 不充分 |
|------|-----------|--------|
| 测试通过 | 测试命令输出：0 失败 | 上次运行、“应该能过” |
| 构建成功 | 构建/`make build` 退出码 0 | lint 通过、日志看着行 |
| Lint 干净 | linter 输出：0 错误 | 局部检查、外推 |
| Bug 已修 | 复现原始症状的测试通过 | 改了代码就假定修好 |
| 回归测试有效 | 红-绿循环验证过 | 只跑过一次通过 |
| 契约同步 | `make generate` 后无 diff | “我改了 openapi.yaml” |
| 端到端通过 | 走完申请→预览→审批→执行→审计 | 只过了单元测试 |

## 危险信号 —— 停

- 用“应该 / 大概 / 看起来”。
- 验证前就表达满意（“搞定！”“完美！”）。
- 没验证就准备提交 / 推送 / 建 PR。
- 信任子任务/其他 Agent 的“成功”报告而不独立核对。
- 只做了局部验证。
- 心想“就这一次”。
- **任何暗示成功却没跑过验证的措辞。**

## 借口对照

| 借口 | 事实 |
|------|------|
| “现在应该好了” | 去运行验证。 |
| “我很有信心” | 信心 ≠ 证据。 |
| “就这一次” | 无例外。 |
| “lint 过了” | lint ≠ 编译器 ≠ 测试。 |
| “子任务说成功了” | 独立核对。 |
| “我累了” | 疲惫不是借口。 |
| “局部检查够了” | 局部证明不了整体。 |
| “换个说法规则就不适用” | 精神高于字面。 |

## 仓库尚未初始化时

若 `make check` 或具体工具尚不存在：
- 运行当前可用的最接近检查。
- 明确列出缺失的验证能力。
- 用“未能验证”，而不是“应该通过”。
- 不为制造绿色结果而跳过、删除或放宽测试。

## 最终报告格式

```text
变更：实际完成的内容
验证：命令及通过/失败结果
未验证：无法执行的检查及原因
风险：仍需人工确认或后续处理的事项
```
